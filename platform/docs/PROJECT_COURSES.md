# Проектные курсы

Документ описывает систему долгосрочных практических курсов в платформе
«Python в облаках». Проектные курсы не заменяют обычные темы и задания: они
возвращают ученика к одному и тому же коду после освоения новых тем.

## Продуктовая концепция

Проектный курс состоит из этапов. Первый вход должен быть ранним: первый этап
`chatbot_to_telegram` открывается после темы 1, чтобы ученик быстро дошёл до
практики. Следующие этапы открываются, когда пользователь прошёл нужные темы
основного курса и завершил предыдущие этапы проекта. На каждом
этапе ученик не начинает с нуля, а продолжает сохранённую программу: добавляет
условия, функции, файлы, словари, JSON, классы или другие изученные навыки.

Главный UX-сигнал: на главной есть постоянная карточка перехода к проектам, а
после релевантной темы появляется предложение
вернуться к проекту. Например: «Вы изучили условия. Теперь можно вернуться к
вашему боту и научить его отвечать по-разному».

Публичный UX-сигнал: готовые или учебные программы можно оформить на общей
доске `#/showcase`. Другие пользователи видят описание, запускают код в
браузере, голосуют облачками от -3 до +3, а лидерборд со временем снижает
старые карточки без новых голосов.

## Архитектура

Система разделена на три слоя.

`project_courses.py` содержит декларативный каталог курсов, этапов, требований,
стартового кода, подсказок и проверок. Там же лежат чистые helper-функции:
вычисление завершённых тем, проверка требований этапа, поиск курса/этапа.
Шестнадцать локальных мини-квестов присоединяются из сгенерированного `practice_quests.json`;
их канонический источник — `python_tasks_collection.md`, не Python-каталог.

`server.py` хранит пользовательское состояние в SQLite и отдаёт JSON API:
список курсов, детальную страницу курса, старт курса, сохранение кода,
завершение этапа, восстановление снимка и предложения вернуться к проекту.

`static/project-courses.js` интегрирует UI в существующую SPA: маршруты
`#/projects`, `#/project/<course_id>`, `#/project/<course_id>/<stage_id>`,
редактор этапа, проверка через серверную одноразовую среду, снимки кода, восстановление и ревью
наставника в модальном окне завершения.

## Модель данных

Таблицы создаются через `CREATE TABLE IF NOT EXISTS` в `SCHEMA`, поэтому
миграция повторяемая и не трогает существующий прогресс.

`project_course_progress`

- `user_id`, `course_id` - курс пользователя;
- `status` - серверный статус курса;
- `current_stage_id` - следующий рабочий этап;
- `started_at`, `completed_at`, `updated_at`.

`project_stage_progress`

- `user_id`, `course_id`, `stage_id` - этап пользователя;
- `status` - `started` или `completed`;
- `current_code` - текущий код этапа;
- `template_version` - версия шаблона этапа;
- `last_check_json` - последний результат проверки;
- `mentor_status` - зарезервировано под состояние ревью.
- `local_evidence_json` - отдельный чек-лист и объяснение локальных действий;
  старой схеме колонка добавляется повторяемым ALTER TABLE с `{}` по умолчанию.

`project_code_snapshots`

- отдельная история версий кода;
- `kind`: `start`, `save`, `complete`, `restore`;
- `version` считается внутри пары пользователь/курс/этап;
- минимально восстановим предыдущий завершённый этап.

`project_course_events`

- продуктовые события и служебные отметки;
- сейчас используется для `prompt_dismissed`, а также логирует просмотры,
  старт, сохранение, завершение и восстановление.

`showcase_cards`

- публичные карточки программ: `title`, `description`, `cover`, `tags_json`;
- `files_json` хранит один или несколько `.py` файлов, основной файл — `main.py`;
- `base_clouds`, `score`, `last_vote_at`, `last_reward_at` поддерживают
  лидерборд, decay старых карточек и ежедневные награды топу.

`showcase_votes`

- один голос пользователя на карточку;
- `value` ограничен диапазоном от -3 до +3;
- повторный голос перезаписывает предыдущий.

## Жизненный цикл курса

1. Курс виден в списке проектов.
2. Пока требования первого этапа не выполнены, статус `unavailable`.
3. Когда первый этап доступен, статус `available`.
4. При старте создаётся запись курса, запись первого этапа и стартовый снимок.
5. После завершения этапа курс переводится на следующий незавершённый этап.
6. Если следующий этап требует ещё не пройденные темы, курс получает статус
   `waiting`.
7. Когда все этапы завершены, курс получает статус `completed`.

## Жизненный цикл этапа

1. Этап доступен только если завершены все предыдущие этапы курса.
2. Дополнительно должны быть пройдены обязательные темы из
   `requirements.topics`.
3. При первом сохранении или старте создаётся строка `project_stage_progress`.
4. Снимок создают старт, явное сохранение с `snapshot: true` и завершение.
   Автосейв и восстановление меняют текущий код без новой версии.
5. Завершённый этап можно открыть снова, изменить код и восстановить старую
   версию из снимка.

## Статусы

API отдаёт стабильный ключ и русскую подпись:

- `unavailable` - недоступен;
- `available` - доступен;
- `started` - начат;
- `waiting` - ожидает изучения нужных тем;
- `continue` - можно продолжить;
- `completed` - завершён.

## Зависимости

Зависимости декларативные. Актуальный пример этапа `commands` квеста
`chatbot_to_telegram`:

```python
{
    "requirements": {"topics": [10, 13]},
    "desired_topics": [15],
    "return_after_topic": 13,
}
```

`requirements.topics` - обязательные темы. Тема считается пройденной, когда
решены все обычные задания этой темы из `tasks_meta.json`.

`desired_topics` - полезный контекст, но не блокирует этап.

`return_after_topic` - тема, после которой стоит показать предложение
вернуться к проекту.

`unlock_topics` относится ко всему курсу, не только к первому этапу; если
поля нет, используются требования первого этапа. Для нового этапа должны
выполниться и требования курса, и `requirements.topics`, и завершение всех
его предыдущих этапов. `desired_topics` и `return_after_topic` эти проверки
не заменяют. Заканчивать соседние проекты ради открытия этого не требуется:
порядок витрины сам по себе не является зависимостью.

Текущая карта с ID и названиями тем для пяти проектов и локальных мини-квестов —
`PROJECT_COURSES_CONTENT.md`. Она сверяется с каталогом и каноническими
названиями тем через `tests/test_project_dependency_docs.py`; старые номера
из раннего контент-плана не являются источником истины.

## UX-потоки

Пользователь впервые видит проекты через пункт навигации «Квесты» и карточку
на главной. На странице курсов отображаются статус, прогресс, конечный результат,
нужные темы для старта и кнопка действия.

На странице курса виден список этапов, их статусы и темы, которые нужно знать.

На странице этапа есть цель, применяемое знание, редактор, кнопки сохранения,
проверки и завершения, подсказки, список снимков и восстановление.

После завершения релевантной обычной темы главная страница показывает карточку
возврата к проекту. Карточку можно открыть или скрыть; скрытие пишется в
`project_course_events`.

Отдельный маршрут `#/showcase` показывает общую доску работ. Страница содержит
seed-карточки, лидерборд, форму публикации, просмотр кода, запуск `main.py` и
голосование. Без `premium_crown` форма принимает один файл; с короной можно
добавлять вспомогательные модули.

## Формат контента

Курс содержит:

- `id`, `title`, `short_title`;
- `quest_label`, `emblem`, `accent` — визуальная идентичность «квеста»
  (эмблема и цветовой акцент в каталоге, деталях и на главной);
- `description`, `intro`, `final_result`;
- `skills`;
- `stages`.

Этап содержит:

- `id`, `title`, `summary`;
- `requirements`, `desired_topics`, `return_after_topic`;
- `new_knowledge`;
- `task`;
- `starter_code`;
- `hints`;
- `check`;
- `return_message`;
- `completion_message`.

## Проверка этапов

Браузер вызывает существующий `PyRunner.run()`, а Python выполняется в
одноразовом серверном контейнере. Старый browser Worker не используется.

Поддержанные типы:

- `expect_contains` - структурная проверка кода;
- `forbid` - запрет преждевременных библиотек или опасных приёмов;
- `append` + `expect` - юнит-проверки, которые дописываются после кода ученика;
- обычный запуск кода, если нет `input()`.

`append` передаётся отдельным аргументом `PyRunner.run(code, onStatus, append)`:
проверка и решение используют одно пространство имён, но отдельные stdout.
Сравнивается `check_stdout`; пользователь видит свой `user_stdout`, без
служебного маркера. Свои примеры и print не мешают тестам функции. Отсутствие
`check_stdout` в несовместимом ответе исполнителя — отказ проверки с предложением обновить страницу.

У мини-квестов `kind: local_practice` функция проверяется в серверной одноразовой
среде; действия с личной IDE и файлами остаются самопроверкой. Для
завершения сервер дополнительно требует `local_evidence: {checked, reflection}`:
все известные уникальные ID чек-листа и объяснение 20–2000 символов. Это
самопроверка, не удостоверение владения IDE. Новых XP/капель и автоматического
ИИ-ревью нет. Восстановление версии кода не откатывает чек-лист; данные видны
только владельцу. Шестнадцать мини-квестов находятся под основной витриной пяти проектов и не
участвуют в их лестнице или автоматических предложениях вернуться после темы.

`practice_file_organizer/preview_copy` добавляет самостоятельную функцию плана
по расширениям и локальную работу с учебными копиями. Нет перемещения/удаления
оригиналов: новая соседняя папка, предварительная проверка и xb без перезаписи.
Реальная дисковая ошибка может оставить частичный результат; чек-лист не является
автоматической проверкой файлов ученика. Эталоны остаются только в каноническом
Markdown и удаляются генератором из публичного practice_quests.json.

`practice_html_report/render_document` — построение небольшого HTML-отчёта:
заголовок, таблица, вычисленный итог и неизменные входы. Текст экранируется в
месте вставки, файловая запись выделена отдельно с режимом x/UTF-8. Проверяется
ограниченный закрытый шаблон, не любой HTML и не универсальная очистка разметки.
Нет стилей, скриптов, внешних ресурсов, публикации или новых наград. Локальное
открытие файла и сохранность JSON остаются самопроверкой ученика.

## Версионирование

Не хранится одна единственная строка кода без истории. Любое важное действие
создаёт снимок. Восстановление меняет `current_code`; само оно не создаёт
ещё одну версию и не откатывает сохранённую самопроверку.

Если шаблон этапа изменится, `template_version` позволит отличать старые
пользовательские решения от новой версии задания. Автоматической миграции кода
пока нет; безопасное поведение - не перезаписывать код пользователя.

## Наставник

`build_review_prompt()` принимает `project_context` как данные:

- название курса;
- название этапа;
- краткое описание предыдущего этапа;
- темы, которые ученик уже должен знать.

Анти-jailbreak правила `REVIEW_SYSTEM` не ослаблены: проектный код и контекст
остаются данными, а не инструкциями.

## Аналитика

Отдельной аналитической системы в проекте нет. Рекомендуемые события пишутся в
`project_course_events` и могут быть выгружены позже:

- `courses_viewed`;
- `course_selected`;
- `course_started`;
- `stage_saved`;
- `stage_completed`;
- `snapshot_restored`;
- `prompt_dismissed`;
- рекомендуемые будущие: `prompt_opened`, `stage_check_failed`,
  `course_completed`, `course_abandoned`.

## Тестирование

Backend покрыт `tests/test_project_courses.py`:

- доступность курса;
- доступность этапа;
- старт курса;
- сохранение кода;
- завершение этапа;
- восстановление снимка;
- предложение вернуться после темы;
- контекст ревью наставника.

Доска работ покрыта `tests/test_showcase.py`: seed-карточки, создание
однофайловой карточки, запрет multi-file без короны, разрешение multi-file с
`premium_crown`, диапазон голосов и пересчёт лидерборда.

Перед завершением работы запускать:

```bash
python -m pytest tests/ -q
node --check static/project-courses.js
node --check static/app.js
```

Для UI вручную проверить:

1. `#/projects`;
2. старт доступного проекта;
3. сохранение этапа;
4. проверку и завершение;
5. модалку с ревью;
6. восстановление снимка;
7. карточку возврата на главной;
8. мобильный viewport.

## Как добавить новый курс

1. Добавить объект курса в `PROJECT_COURSES` в `project_courses.py`.
2. Выбрать устойчивый `id` в нижнем регистре через подчёркивания.
3. Описать конечный продукт и список `skills`.
4. Добавить этапы с `requirements.topics`.
5. Для каждого этапа указать `starter_code`, подсказки и проверку.
6. Проверить примерный финальный код в CPython 3.14, если этап содержит
   исполняемую проверку.
7. Добавить тест доступности или сценарий API в `tests/test_project_courses.py`.
8. Обновить `docs/PROJECT_COURSES_CONTENT.md`.
9. Запустить pytest и graphify.

## Как добавить новый этап

1. Вставить этап в нужное место массива `stages`.
2. Не полагаться только на позицию: указать `requirements.topics`.
3. Если этап должен появиться после конкретной темы, указать
   `return_after_topic`.
4. Стартовый код должен либо работать сам по себе, либо быть понятной заготовкой.
5. Проверка должна принимать несколько разумных способов решения.
6. Нельзя перезаписывать код пользователя при изменении этапа; повышайте
   `template_version` и документируйте миграцию.
